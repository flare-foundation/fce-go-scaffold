# Extension template

The minimal starting point for an extension: one placeholder op on each channel, and no state.
A fork turns it into its own extension.

## Layout

- `cmd/extension/main.go`: the entrypoint; it reads the environment, registers the ops and serves tee-node until stopped.
- `internal/app`: the extension's own code: op constants, handlers, and their tests.
- `conformance/`: golden fixtures, generated by `internal/app/fixtures_test.go`.
- `contracts/`: the entrypoint contract, `InstructionSender`, its deploy and post-registration scripts, and its forge tests; see [contracts.md](../docs/contracts.md).
- `Dockerfile`: the TEE image: the launcher as PID 1, tee-node as root, and the extension as a non-root user; built with the repository root as context.
  The lines after a `# per extension:` comment are the extension's own.

## Ops

Each op pair belongs to one channel, instructions or direct actions, never both.

| Op type | Op command | Channel | Payload | Result |
|---|---|---|---|---|
| `MY_EXTENSION` | `MY_COMMAND` | instruction | `abi.encode(address sender, bytes message)` | the same pair, ABI-encoded |
| `MY_EXTENSION` | `MY_DIRECT_COMMAND` | direct | JSON `{"message": "…"}` | the same JSON |

A payload that doesn't decode answers `status 0` with the log `error: invalid payload`, and an empty message `error: message required`.
`MY_COMMAND` accepts only the canonical ABI encoding, as the contract's `abi.encode` produces it.
`MY_DIRECT_COMMAND` refuses unknown fields and anything after the JSON value.

### `MY_COMMAND`

A caller sends it through `InstructionSender.myCommand(bytes message)`, paying at least `quoteFee(OP_TYPE_MY_EXTENSION, OP_COMMAND_MY_COMMAND)`; the contract keeps any excess.
The contract encodes the caller, `msg.sender`, with the message: tee-node doesn't pass the caller to the extension.
[`conformance/my-command.json`](conformance/my-command.json) holds a sample payload and its result.

### `MY_DIRECT_COMMAND`

A client posts it to the proxy's `POST /direct`, with the op type and command as bytes32 and the payload as hex:

```json
{
  "opType": "0x4d595f455854454e53494f4e0000000000000000000000000000000000000000",
  "opCommand": "0x4d595f4449524543545f434f4d4d414e44000000000000000000000000000000",
  "message": "0x7b226d657373616765223a2268656c6c6f227d"
}
```

The message is `{"message":"hello"}`, and so is the result's `data`.
The proxy accepts direct actions only when its operator enables them, and then from anyone holding its API key, or from anyone if the key is optional.
Who may trigger the command is a `TODO` in the handler.
Anyone who saw a direct action can post it again, so each direct command is idempotent or refuses replays; see [direct actions](../docs/direct-actions.md).

## Testing

```bash
go test ./template/...                           # the handlers, and the fixtures are current
go test ./template/internal/app -update          # rewrite the fixtures after changing them
make test                                        # also runs the contract's forge tests
fce conformance ./template                       # build the binary and check it from the outside
fce image ./template                             # build the image as attested and print its config digest
fce repro ./template                             # build it twice without cache; the digests must match
fce image-check ./template                       # build the image, then check it from the outside
```

`fce conformance`, from the tooling repo, starts the binary against a fake sign port, sends it each fixture as tee-node would, and runs the checks every extension must pass.
The forge tests read `conformance/my-command.json` too, and check that the contract builds exactly its op pair and payload.
[Testing](../docs/testing.md) covers every layer.

## Deploying

```bash
fce deploy -chain coston2 -account <name> ./template                                # deploy the contract, register it, bind its id
fce add-version -chain coston2 -account <name> -platform GCP_AMD_SEV ./template     # allow the image's hash on a platform
fce governance -chain coston2 -account <name> -signers 0x… -threshold 1 ./template  # the signers that govern its machines
fce status -chain coston2 ./template                                                # compare the record with the chain
```

`fce` signs with a Foundry keystore account and keeps what it did in `deployments/coston2.json`; commit it, so the extension's addresses are published with its code.
The tooling repo's README describes each command.

## Running

A test machine runs tee-node in test mode, so the extension needs a test version as well as the governance above; tee-proxy reads the chain through the RPC, or from an indexer's database with `-indexer-db`, as the tooling repo's README describes:

```bash
fce add-version -chain coston2 -account <name> -test ./template                    # allow tee-node's test hash on TEST_PLATFORM
fce run -chain coston2 -account <name> ./template                                  # a test machine in production; shows its logs
fce send -chain coston2 -account <name> ./template 'myCommand(bytes)' 0x68656c6c6f  # "hello"; the result is abi.encode(sender, message)
fce direct -chain coston2 ./template MY_EXTENSION MY_DIRECT_COMMAND 0x7b226d657373616765223a2268656c6c6f227d  # {"message":"hello"}
```

`fce run` stays attached; send from a second terminal.
Ctrl-C pauses the machine on chain and removes it.
A test machine has no TEE, and its key sits in a container on your host: keep the test version off an extension real users use, or disable it, `fce disable-version -test`, before they arrive.
